**Data:** 10 agosto 2026
**Stato progetto:** reverse engineering protocollo in corso. Lettura funzionante, scrittura NON funzionante.
**Scopo di questo documento:** permettere a un nuovo agente (Claude Code) di riprendere il lavoro senza rifare le indagini già svolte.

## 1. OBIETTIVO

Costruire un'applicazione personale per **controllare e organizzare i preset dello Spark 2** in modo arbitrario, senza i vincoli dell'app ufficiale Positive Grid.

**Funzionalità target:**
- Libreria preset locale con organizzazione libera: categorie/tag custom, preferiti, note personali, ricerca full-text, ordinamento manuale
- Editor della catena effetti (noise gate → comp → drive → amp → mod → delay → reverb) con modello + parametri per blocco
- Invio preset/parametri all'ampli e lettura in tempo reale dello stato dell'ampli
- Backup/export/import in JSON

**Utente:** singolo utente (l'autore), uso personale, non distribuzione pubblica.

**Piattaforma decisa:** **web app / PWA su Android**.
- iPad era la richiesta iniziale ma è stata **scartata**: Safari iOS non supporta Web Bluetooth, e senza un Mac non è possibile compilare un'app nativa iOS.
- Android è stato scelto perché Chrome per Android supporta Web Bluetooth, permettendo di restare su HTML/JS single-file senza toolchain nativa.

## 3. CONOSCENZE SULL'HARDWARE (Spark 2)

### 3.1 Trasporto

Lo Spark 2 espone **due connessioni Bluetooth distinte**:
- `Spark 2 Audio` — Bluetooth Classic A2DP, solo streaming audio. Si accoppia dalle impostazioni Bluetooth del telefono. **Non usata da questo progetto.**
- `Spark 2 BLE` — Bluetooth Low Energy, canale di controllo ("Tone Control"). **È quella che usiamo.** Il nome esatto restituito da `device.name` è la stringa `Spark 2 BLE`.

La documentazione ufficiale Positive Grid indica che il Tone Control usa BLE **sia su iOS che su Android** (contrariamente alla documentazione di reverse engineering di Hamshere, scritta per lo Spark 40, che indicava Bluetooth Classic per Android).

Lo Spark 2 ha anche una porta **USB-C** e supporta un pedale wireless proprietario ("Spark Control X"), entrambi non ancora indagati.

### 3.2 GATT — UUID verificati sul dispositivo reale

```
Service:                  0xFFC0
Characteristic scrittura: 0xFFC1
Characteristic notifiche: 0xFFC2
```

**Proprietà rilevate a runtime sulla characteristic 0xFFC1:**
```
write                 = false
writeWithoutResponse  = true
```
→ Va usato obbligatoriamente `writeValueWithoutResponse()`. Non esiste conferma a livello GATT, quindi un messaggio malformato o rifiutato non produce **nessun** errore: fallisce in silenzio.

Le notifiche su 0xFFC2 vanno abilitate con `startNotifications()`. L'ampli frammenta le notifiche lunghe in pacchetti da ~20 byte: **serve riassemblaggio** cercando `0xF0` come inizio e `0xF7` come fine.

### 3.3 Formato pacchetto (chunk) — VERIFICATO

```
offset  len  contenuto
  0      1   0xF0                  (inizio, stile MIDI SysEx)
  1      1   0x01                  (fisso)
  2      1   sequence number       (incrementa a ogni messaggio)
  3      1   checksum              (XOR 8 bit dei soli byte dati)
  4      1   command
  5      1   sub-command
  6      n   dati (codifica 7bit/8bit, vedi 3.4)
 6+n     1   0xF7                  (fine)
```

**Checksum — algoritmo verificato a mano contro cattura reale.**
È lo XOR a 8 bit di **tutti e soli i byte dati** (offset 6 fino a 6+n-1), escludendo header `F0 01 seq cs cmd sub` ed escludendo il trailer `F7`. I byte "bits8" della codifica 7/8 bit **sono inclusi** nello XOR.

Verifica su messaggio reale dell'ampli:
```
f0 01 6a 7a 03 37 02 0b 2b 62 69 61 73 2e 00 72 65 76 65 72 62 00 11 4a 3f 5c 1f 5c 00 f7
                 ^^ checksum dichiarato = 0x7a
XOR di: 02 0b 2b 62 69 61 73 2e 00 72 65 76 65 72 62 00 11 4a 3f 5c 1f 5c 00 = 0x7a  ✓
```

Nota dal changelog di Hamshere: *l'app è sensibile al checksum ma **l'ampli non sembra usarlo**.* Quindi un checksum errato probabilmente non è causa di rifiuto lato ampli.

### 3.4 Codifica dati 7bit/8bit (stile SysEx Ruin & Wesen) — VERIFICATA

I byte dati non possono avere il bit 7 impostato. Ogni gruppo di **7 byte reali** è preceduto da un byte "bits8" che contiene gli ottavi bit mancanti, **ordine LSB-first**:

```
bits8 bit i  =  MSB del byte i-esimo del gruppo (i = 0..6)
byte trasmesso = byte reale & 0x7F
```

Encoder JS (già implementato e verificato byte-per-byte contro le catture):
```javascript
function pack7bit8bit(dataBytes) {
  const out = [];
  for (let i = 0; i < dataBytes.length; i += 7) {
    const group = dataBytes.slice(i, i + 7);
    let bits8 = 0;
    const stripped = group.map((b, idx) => {
      if (b & 0x80) { bits8 |= (1 << idx); return b & 0x7f; }
      return b;
    });
    out.push(bits8, ...stripped);
  }
  return out;
}
```

### 3.5 Tipi dati (msgpack "rotto")

| Tipo | Lunghezza | Formato | Primo byte |
|---|---|---|---|
| Short integer | 1 | valore diretto | 0x00–0x7F |
| Integer | 2 | `0xCC` + valore | 0xCC |
| Fixed array | n+1 | `0x90 + n` | 0x90–0x9F |
| Short string | n+1 | `0xA0+len` + ASCII | 0xA0–0xBF |
| **Alternative short string** | n+2 | `len`, `0xA0+len`, ASCII | 0x01–0x1F |
| Long string | n+2 | `0xD9`, len, ASCII | 0xD9 |
| Boolean off | 1 | `0xC2` | 0xC2 |
| Boolean on | 1 | `0xC3` | 0xC3 |
| Float | 5 | `0xCA` + 4 byte IEEE-754 **big endian** | 0xCA |

I valori dei parametri sono sempre **float 0.0–1.0**, dove `1.0` corrisponde a "10" nell'interfaccia utente. Valori fuori range vengono presumibilmente scartati.

### 3.6 Block header (trasporto seriale) — NON necessario su BLE

Documentato per Bluetooth Classic. 16 byte prima del chunk:
```
01 fe 00 00 | 53 fe | <size> | 00 00 00 00 00 00 00 00 00
             ^^^^^ direzione: 53 fe = verso l'ampli, 41 ff = dall'ampli
                     ^^^^^^ dimensione blocco totale incluso header
```
**Evidenza raccolta:** su BLE le notifiche in arrivo dall'ampli **non contengono** questo header (iniziano direttamente con `F0 01`), e i comandi GET inviati **senza** header ricevono regolare risposta. Conclusione: su BLE il block header non serve. Testato anche **con** header sui comandi di scrittura → nessuna differenza (entrambi ignorati).

### 3.7 Comandi

**Verso l'ampli (cmd 0x01 = azioni, 0x02 = query):**

| cmd | sub | Significato | Risposta attesa |
|---|---|---|---|
| 01 | 01 | Invia preset completo (multi-chunk) | ack |
| 01 | 04 | **Cambia parametro effetto** | nessuna |
| 01 | 06 | Cambia modello effetto | ack |
| 01 | 15 | Abilita/disabilita effetto | ack |
| 01 | 38 | Cambia preset hardware | ack |
| 01 | 70 | **Invia license key** | ack |
| 02 | 01 | Leggi preset | dati preset |
| 02 | 10 | Leggi preset hw corrente | numero preset |
| 02 | 11 | Leggi nome ampli | stringa |
| 02 | 23 | Leggi numero seriale | stringa |
| 02 | 2a | Leggi checksum preset | array di 4 int |
| 02 | 2f | Leggi versione firmware | uint32 |

**Dall'ampli (cmd 0x03 = notifiche, 0x04/0x05 = ack):**

| cmd | sub | Significato |
|---|---|---|
| 03 | 01 | Dati preset |
| 03 | 06 | Cambio modello effetto sull'ampli |
| 03 | 10 | Preset hw corrente |
| 03 | 11 | Nome ampli |
| 03 | 15 | Effetto abilitato/disabilitato |
| 03 | 23 | Numero seriale |
| 03 | 27 | Preset salvato in memoria hw |
| 03 | 2a | Checksum preset |
| 03 | 2f | Versione firmware |
| 03 | 37 | **Cambio parametro sull'ampli** (manopola girata) |
| 03 | 38 | Cambio preset sull'ampli |
| 03 | 63 | Tap tempo |
| 04 | nn | Ack (stesso sub-command e sequence del comando ricevuto) |
| 05 | 01 | Ack chunk finale preset |

**IMPORTANTE — errore commesso e da non ripetere:** i messaggi `0x03xx` sono **solo** ampli→app. Rispedirli identici all'ampli non funziona (fatto, ignorato in silenzio). Per scrivere si usa `0x01xx`.

### 3.8 Payload dei comandi chiave

**`0x0104` — cambia parametro effetto** (dati prima della codifica 7/8 bit):
```
[alt short string: nome effetto] [short int: numero parametro] [0xCA + float32 BE]
```

**`0x0115` — abilita/disabilita effetto:**
```
[alt short string: nome effetto] [0xC2 off | 0xC3 on]
```

**`0x0138` — cambia preset hardware:**
```
[short int: 0x00] [short int: numero preset]
```

**`0x0106` — cambia modello effetto:**
```
[alt short string: vecchio nome] [alt short string: nuovo nome]
```

**`0x0201` — leggi preset:**
```
[int 2 byte: 0x0000-0x0003 = preset hw | 0x007F = preset software | 0x0100 = stato live]
[30 byte 0x00]
```

### 3.9 Catture reali dal dispositivo (byte letterali)

**Manopola reverb girata (`0337`):**
```
f0 01 6a 7a 03 37 02 0b 2b 62 69 61 73 2e 00 72 65 76 65 72 62 00 11 4a 3f 5c 1f 5c 00 f7
```
Decodifica: `0x0b 0xab` = alt short string len 11 → `bias.reverb`; poi `0x00` = parametro 0; poi `0xCA` + `3f 5c 1f dc` = float **0.8598**.
→ **La manopola fisica del reverb è il parametro 0 di `bias.reverb`.**

Progressione catturata girando la manopola da minimo a massimo:
```
00 00 00 00 → 0.000000   (minimo esatto)
3d 36 30 36 → 0.044480
3e 53 34 54 → 0.206254
3f 00 0f 01 → 0.500229
3f 4b 71 4b → 0.794697
3f 73 50 74 → 0.950446
3f 7f 7e 00 → 0.998016   (massimo)
```

**Nome ampli (`0311`):**
```
f0 01 01 6b 03 11 02 07 27 53 70 61 72 6b 00 20 32 f7
```
→ alt short string len 7 → `Spark 2`

**Numero seriale (`0323`):**
```
f0 01 02 02 03 23 02 0f 2f 53 35 30 31 31 00 47 31 34 38 31 34 33 00 39 37 34 f7
```
→ stringa `S5011G148143974`

**Versione firmware (`032f`):**
```
f0 01 05 10 03 2f 11 4e 02 07 02 48 f7
```
→ dati decodificati `ce 02 07 02 c8` = msgpack uint32. Interpretazione non confermata.

**Preset hw corrente (`0310`):**
```
f0 01 05 06 03 10 00 00 06 f7
```
→ dati `00 06`. **Attenzione: valore 6, non 0-3.** Vedi problemi aperti.

**Messaggio `031a` — NON DOCUMENTATO, emesso ripetutamente durante il movimento delle manopole:**
```
f0 01 xx 5e 03 1a 09 11 00 05 43 f7
f0 01 xx 5d 03 1a 09 11 00 06 43 f7
```
Il penultimo byte dati alterna tra `05` e `06`. Funzione ignota (heartbeat? ack interno?).

### Cosa FUNZIONA (verificato sul dispositivo reale)

- Connessione BLE via Web Bluetooth da Chrome Android
- Sottoscrizione notifiche su 0xFFC2
- Riassemblaggio dei messaggi frammentati (`F0`…`F7`)
- Decodifica: nomi effetti, nome ampli, seriale, float dei parametri
- **Tutti i comandi di lettura `0x02xx` funzionano e ricevono risposta corretta**: nome ampli, seriale, preset 0/1/2/3, preset corrente, versione firmware, stato live

### Cosa NON funziona

- **Nessun comando di scrittura ha effetto sull'ampli.** Specificamente `0x0104` (cambio parametro), testato con:
  - con e senza block header
  - sequence number fisso, incrementale, sincronizzato con RX
  - `writeValueWithoutResponse` (unico metodo supportato)
  - frammentazione in pacchetti da 20 byte con pausa da 30 ms
  - parametri 0–6, valori 0.0–1.0
  - dopo aver eseguito l'intera sequenza di handshake
  
  In tutti i casi: **nessun errore GATT, nessuna risposta, nessun effetto udibile o visibile.**
- `0x022a` (leggi checksum preset) non riceve risposta — probabilmente perché i dati vanno incapsulati in un fixarray `0x94` che non stiamo inviando.
- Il test `0x0138` (cambio preset) **è stato implementato ma il suo risultato non è mai stato riportato**. È il test diagnostico più importante ancora da eseguire.

## 6. PROBLEMI APERTI

### 6.1 Perché le scritture vengono ignorate — ipotesi in ordine di plausibilità

1. **License key (`0x0170`) mai inviata.** L'Appendice 3 della documentazione mostra che l'app ufficiale invia una chiave di licenza da 64 byte durante lo startup, prima di qualsiasi comando. È plausibile che l'ampli accetti letture da chiunque ma rifiuti scritture da client non autenticati. **Questa è l'ipotesi principale.** Non sappiamo se la chiave sia costante, derivata dal seriale, o per-sessione.
2. **Il firmware dello Spark 2 differisce dallo Spark 40.** Tutta la documentazione di reverse engineering riguarda lo Spark 40 (2020). Lo Spark 2 è un modello successivo: i comandi di lettura sono chiaramente compatibili, ma quelli di scrittura potrebbero essere cambiati o protetti.
3. **Frammentazione/MTU.** I messaggi che funzionano sono ≤12 byte; quelli che falliscono sono ≥28. Mitigato dividendo in pacchetti da 20 byte, senza risultato — ma la strategia di frammentazione potrebbe comunque essere sbagliata.
4. **Ordinamento dei bit nella codifica 7/8 bit in scrittura.** L'encoder è verificato in *decodifica* contro i messaggi dell'ampli, ma la libreria Arduino MIDI espone un flag `inFlipHeaderBits`: se l'ampli si aspettasse l'ordine opposto in ricezione, i messaggi lunghi risulterebbero corrotti mentre quelli corti (senza byte con MSB alto) resterebbero validi. **Questa ipotesi spiega elegantemente il pattern osservato e non è ancora stata testata.**

### 6.2 Numerazione preset dello Spark 2

L'ampli riporta il preset corrente come `06`, non nel range 0–3 documentato per lo Spark 40. Lo Spark 2 potrebbe avere **8 preset hardware**. Da verificare prima di usare `0x0138`.

### 6.3 Byte e comandi ignoti

- Comando `0x031a` (non documentato, vedi 3.9)
- Byte 1 del chunk (`0x01`, sempre costante — significato ignoto)
- Trailing `0x00` presente nei messaggi `0x0337` dell'ampli dopo il float, assente nell'esempio della documentazione

### 6.4 Decisioni da prendere

- **Se le scritture BLE restano impossibili**, scegliere tra:
  - **(a) Bridge ESP32** — usare `paulhamsh/Spark` (già funzionante e testato da terzi) su un ESP32 che parla col'ampli e espone un'API HTTP/WebSocket in WiFi; la web app resta HTML e parla con l'ESP32. *Costo: hardware + firmware. Beneficio: aggira ogni limite del browser.*
  - **(b) App nativa Android** (Kotlin) — accesso a RFCOMM e a MTU negoziabile. *Costo: nuova toolchain, abbandono dello stack HTML.*
  - **(c) USB MIDI** — lo Spark 2 ha USB-C; esiste il progetto `spark-usb-midi`. Da browser si userebbe la Web MIDI API. *Costo: da verificare se lo Spark 2 espone una porta MIDI USB. Beneficio: resterebbe tutto in web app.*
  - **(d) Sola lettura** — costruire comunque la libreria preset e l'organizzazione, usando l'app ufficiale per l'invio. Ripiego.
- Se si procede con la web app: confermare IndexedDB come storage e definire lo schema dei preset.

## 7. PROSSIMI PASSI (in ordine)

1. **Eseguire il test `0x0138` (cambio preset)** già implementato in `spark-ble-explorer.html`. È il discriminante: messaggio corto come quelli che funzionano, ma è una *scrittura* con effetto visibile (LED preset). 
   - Se **funziona** → le scritture passano; il problema è nei messaggi lunghi → andare al punto 2.
   - Se **fallisce** → tutte le scritture sono rifiutate → ipotesi license key/firmware → andare al punto 4.
   - *Nota: provare valori sia 0–3 sia 4–7, vista l'anomalia del preset `06`.*

2. **Testare l'ordinamento inverso dei bit** nella codifica 7/8 bit in scrittura (`bits8 |= 1 << (6 - idx)` invece di `1 << idx`). Modifica di una riga, alta probabilità di essere la causa se il punto 1 ha successo.

3. **Testare `0x0115`** (abilita/disabilita effetto su `bias.reverb` con `0xC2`/`0xC3`): messaggio di lunghezza intermedia con effetto udibile immediato, utile per isolare la soglia di lunghezza.

4. **Catturare il traffico dell'app ufficiale.** È l'unico modo per risolvere definitivamente la questione license key e vedere i byte esatti di una scrittura che funziona.
   - Lo sniffing HCI da Android è già stato tentato senza successo (il file `btsnoop_hci.log` non è accessibile né via bug report né via ADB senza root sui dispositivi provati).
   - Alternative: dispositivo Android con root; sniffer BLE hardware (nRF52840 dongle + Wireshark, ~20 €); decompilazione dell'APK ufficiale per estrarre la logica della license key.

5. **Verificare la via USB MIDI**: collegare lo Spark 2 via USB-C a un PC e controllare se compare come dispositivo MIDI. Se sì, testare `navigator.requestMIDIAccess()` da Chrome — aggirerebbe completamente il problema BLE restando nello stack web.

6. **Solo dopo aver risolto la scrittura**, iniziare l'app vera:
   - modulo `spark-protocol.js` (encoder/decoder puro, senza I/O)
   - modulo `spark-transport.js` (connessione, frammentazione, code di invio)
   - modulo `preset-store.js` (IndexedDB: preset, tag, note, preferiti)
   - UI (lista organizzabile + editor catena effetti)

7. Portare in `spark-protocol.js` anche il **parser dei preset completi** (`0x0301`), che arrivano già correttamente ma non sono ancora decodificati in struttura: sono multi-chunk, con sub-header a 3 byte (totale chunk, indice chunk, dimensione) e checksum finale come somma modulo 256.

## 8. NOTA OPERATIVA PER CHI RIPRENDE

Il tool si testa così: aprire il file in Chrome su Android (o servirlo via https), accendere lo Spark 2 in modalità pairing, premere "Connetti allo Spark", selezionare `Spark 2 BLE`. Le manopole fisiche generano traffico immediato, utile per validare qualsiasi modifica al decoder.

Attenzione: **l'assenza di errori non significa successo.** Con `writeWithoutResponse` ogni scrittura appare riuscita lato browser. L'unica verifica valida è l'effetto sull'ampli o una risposta in RX.

function nowStr() {
  const d = new Date();

function bytesToHex(bytes) {
  return Array.from(bytes).map(b => b.toString(16).padStart(2, '0')).join(' ');
}

function hexToBytes(hexStr) {
  const clean = hexStr.trim().split(/\s+/).filter(Boolean);

// --- Riassemblaggio messaggi frammentati (BLE MTU spezza i pacchetti lunghi) ---
let msgBuffer = [];
let lastSeenSeq = null;
let txSeqCounter = null; // contatore di sequenza indipendente per i nostri invii

function handleFragment(bytes) {
  for (const b of bytes) {
    // Se il buffer è vuoto, aspettiamo l'inizio F0
    if (msgBuffer.length === 0) {
      if (b === 0xf0) msgBuffer.push(b);
      // altrimenti scartiamo byte orfani prima di un F0
      continue;
    }
    msgBuffer.push(b);
    if (b === 0xf7) {
      // messaggio completo
      onCompleteMessage(new Uint8Array(msgBuffer));
      msgBuffer = [];
    }
  }
}

function extractAsciiRuns(bytes, minLen = 3) {
  const runs = [];
  let current = '';
  for (const b of bytes) {
    if (b >= 0x20 && b <= 0x7e) {
      current += String.fromCharCode(b);
    } else {
      if (current.length >= minLen) runs.push(current);
      current = '';
    }
  }
  if (current.length >= minLen) runs.push(current);
  return runs;
}

function onCompleteMessage(bytes) {
  const div = document.createElement('div');
  div.className = 'entry rx';
  div.style.borderLeft = '3px solid #4a9eff';
  div.style.paddingLeft = '8px';
  div.style.marginTop = '4px';

  const seq = bytes.length > 2 ? bytes[2] : null;
  const cmd = bytes.length > 5 ? bytes[5] : null;
  const ascii = extractAsciiRuns(bytes);

  if (seq !== null) {
    lastSeenSeq = seq; // teniamo traccia dell'ultimo numero di sequenza visto dall'ampli
    txSeqCounter = (seq + 1) & 0xff; // sincronizziamo anche il contatore TX
  }

  let html = `<span class="t">[${nowStr()}]</span> <span class="tag" style="color:#4a9eff">MSG completo</span> `;
  html += `len=${bytes.length}`;
  if (seq !== null) html += ` seq=0x${seq.toString(16)}`;
  if (cmd !== null) html += ` cmd(ipotesi)=0x${cmd.toString(16)}`;
  html += `<br><span class="hex" style="color:#7fe08a">${bytesToHex(bytes)}</span>`;
  if (ascii.length > 0) {
    html += `<br><span style="color:#f0d060">testo estratto: ${ascii.map(s => '"' + s.replace(/</g,'&lt;') + '"').join(', ')}</span>`;
  }
  // Ipotesi: nei messaggi cmd 0x37, i 4 byte immediatamente prima di "00 f7" finale
  // sembrano codificare un parametro come float32 big-endian (range 0.0-1.0)
  if (cmd === 0x37 && bytes.length >= 8 && bytes[bytes.length - 2] === 0x00 && bytes[bytes.length - 1] === 0xf7) {
    const fbytes = bytes.slice(bytes.length - 6, bytes.length - 2);
    if (fbytes.length === 4) {
      const buf = new ArrayBuffer(4);
      const dv = new DataView(buf);
      fbytes.forEach((b, i) => dv.setUint8(i, b));
      const floatVal = dv.getFloat32(0, false); // big-endian
      html += `<br><span style="color:#c080ff">float32 ipotizzato (byte ${bytesToHex(fbytes)}): ${floatVal.toFixed(6)}</span>`;
    }
  }
  div.innerHTML = html;
  logEl.appendChild(div);
  logEl.scrollTop = logEl.scrollHeight;
}

    setStatus('connecting', 'Ricerca dispositivo...');

    setStatus('connecting', 'Connessione GATT...');

    logInfo('Proprietà characteristic scrittura (0xFFC1): write=' + writeChar.properties.write +

      handleFragment(bytes);

    btnSend.disabled = false;

    logInfo('Errore invio (GATT): ' + err.message);
  }

// --- Encoder per messaggi in scrittura (comando 0x0104 - change effect parameter) ---
// Basato su: Spark Protocol Description v3.1 (Paul Hamshere)

function floatToBytesBE(val) {
  const buf = new ArrayBuffer(4);
  const dv = new DataView(buf);
  dv.setFloat32(0, val, false); // big-endian
  const out = [];
  for (let i = 0; i < 4; i++) out.push(dv.getUint8(i));
  return out;
}

// Codifica "alternative short string": [len, len+0xa0, ...ascii bytes]
function encodeAltShortString(str) {
  const len = str.length;
  const bytes = [len, len + 0xa0];
  for (let i = 0; i < str.length; i++) bytes.push(str.charCodeAt(i));
  return bytes;
}

// Applica la codifica 7bit/8bit stile SysEx: ogni 7 byte di dati reali
// sono preceduti da un byte "bits8" con gli ottavi bit mancanti
function pack7bit8bit(dataBytes) {
  const out = [];
  for (let i = 0; i < dataBytes.length; i += 7) {
    const group = dataBytes.slice(i, i + 7);
    let bits8 = 0;
    const stripped = group.map((b, idx) => {
      if (b & 0x80) {
        bits8 |= (1 << idx);
        return b & 0x7f;
      }
      return b;
    });
    out.push(bits8, ...stripped);
  }
  return out;
}

function xorChecksum(bytes) {
  let cs = 0;
  for (const b of bytes) cs ^= b;
  return cs & 0xff;
}

function buildChangeParamMessage(effectName, paramNum, floatVal, seq) {
  // Costruisce i dati logici: nome effetto + numero parametro + valore float
  const rawData = [
    ...encodeAltShortString(effectName),
    paramNum & 0x7f,          // Short Integer (0x00-0x7f)
    0xca, ...floatToBytesBE(floatVal)  // Float: prefisso 0xca + 4 byte big-endian
  ];

  const packedData = pack7bit8bit(rawData);
  const checksum = xorChecksum(packedData);

  // Chunk: f0 01 <seq> <checksum> 01 04 <packedData> f7
  const chunk = [0xf0, 0x01, seq & 0xff, checksum, 0x01, 0x04, ...packedData, 0xf7];

  // Header di blocco (documentato per il trasporto seriale classico):
  // 01 fe 00 00 | direzione (53 fe = verso l'ampli) | dimensione blocco | 9 zeri
  const blockSize = (16 + chunk.length) & 0xff; // 16 byte header + lunghezza chunk
  const blockHeader = [0x01, 0xfe, 0x00, 0x00, 0x53, 0xfe, blockSize, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00];

  return { withBlockHeader: [...blockHeader, ...chunk], chunkOnly: chunk };
}

async function sendParamChange() {
  if (!writeChar) {
    logInfo('Non connesso.');
    return;
  }
  const effName = document.getElementById('effName').value.trim();
  const paramNum = parseInt(document.getElementById('paramNum').value, 10) || 0;
  let paramVal = parseFloat(document.getElementById('paramVal').value);
  if (!effName || isNaN(paramVal)) {
    logInfo('Compila nome effetto e valore validi.');
    return;
  }
  // Il protocollo accetta solo valori 0.0-1.0 (1.0 = "10" nell'interfaccia utente)
  if (paramVal < 0 || paramVal > 1) {
    const clamped = Math.max(0, Math.min(1, paramVal));
    logInfo(`ATTENZIONE: valore ${paramVal} fuori range (ammesso 0.0-1.0). Uso ${clamped}.`);
    paramVal = clamped;
  }

  const seq = (txSeqCounter !== null ? txSeqCounter : (lastSeenSeq !== null ? lastSeenSeq + 1 : 1)) & 0xff;
  txSeqCounter = (seq + 1) & 0xff;
  const msg = buildChangeParamMessage(effName, paramNum, paramVal, seq);
  const useBlockHeader = document.getElementById('chkBlockHeader').checked;
  const fullBytes = useBlockHeader ? msg.withBlockHeader : msg.chunkOnly;

  try {
    await sendInMtuChunks(fullBytes);
    logInfo(`Inviato cmd 0x0104 (${useBlockHeader ? 'con' : 'senza'} header blocco, spezzato in pacchetti da max 20 byte): effetto="${effName}" param=${paramNum} valore=${paramVal} (seq=0x${seq.toString(16)})`);
    logEntry('tx', new Uint8Array(fullBytes));
  } catch (err) {
    logInfo('Errore invio parametro: ' + err.message);
  }
}

// Spezza un array di byte in scritture BLE separate da max 20 byte ciascuna,
// per evitare il troncamento silenzioso dovuto all'MTU di default
async function sendInMtuChunks(byteArray, maxChunk = 20) {
  for (let i = 0; i < byteArray.length; i += maxChunk) {
    const slice = new Uint8Array(byteArray.slice(i, i + maxChunk));
    if (writeChar.properties.write) {
      await writeChar.writeValueWithResponse(slice);
    } else {
      await writeChar.writeValueWithoutResponse(slice);
    }
    logInfo(`  → pacchetto BLE inviato (${slice.length} byte): ${bytesToHex(slice)}`);
    // piccola pausa: writeWithoutResponse non ha controllo di flusso,
    // pacchetti troppo ravvicinati possono essere persi
    if (i + maxChunk < byteArray.length) await new Promise(r => setTimeout(r, 30));
  }
}

// --- Handshake iniziale: sequenza di messaggi GET che l'app ufficiale manda alla connessione ---
function buildSimpleGetMessage(cmd, subcmd, dataBytes, seq) {
  const data = dataBytes || [];
  const packedData = pack7bit8bit(data);
  const checksum = xorChecksum(packedData);
  return [0xf0, 0x01, seq & 0xff, checksum, cmd, subcmd, ...packedData, 0xf7];
}

async function sendHandshake() {
  if (!writeChar) {
    logInfo('Non connesso.');
    return;
  }
  // Sequenza ispirata all'Appendice 3 del documento di protocollo
  const steps = [
    { cmd: 0x02, sub: 0x11, data: [], desc: 'Get amp name' },
    { cmd: 0x02, sub: 0x2a, data: [0x00, 0x01, 0x02, 0x03], desc: 'Get preset checksums' },
    { cmd: 0x02, sub: 0x23, data: [], desc: 'Get serial number' },
    { cmd: 0x02, sub: 0x01, data: [0x00, 0x00], desc: 'Get preset 0' },
    { cmd: 0x02, sub: 0x01, data: [0x00, 0x01], desc: 'Get preset 1' },
    { cmd: 0x02, sub: 0x01, data: [0x00, 0x02], desc: 'Get preset 2' },
    { cmd: 0x02, sub: 0x01, data: [0x00, 0x03], desc: 'Get preset 3' },
    { cmd: 0x02, sub: 0x10, data: [], desc: 'Get current hardware preset' },
    { cmd: 0x02, sub: 0x2f, data: [], desc: 'Get firmware version' },
    { cmd: 0x02, sub: 0x01, data: [0x01, 0x00], desc: 'Get current amp settings (live state)' },
  ];

  for (const step of steps) {
    const seq = (txSeqCounter !== null ? txSeqCounter : (lastSeenSeq !== null ? lastSeenSeq + 1 : 1)) & 0xff;
    txSeqCounter = (seq + 1) & 0xff;
    const bytes = new Uint8Array(buildSimpleGetMessage(step.cmd, step.sub, step.data, seq));
    try {
      if (writeChar.properties.write) {
        await writeChar.writeValueWithResponse(bytes);
      } else {
        await writeChar.writeValueWithoutResponse(bytes);
      }
      logInfo(`Handshake: inviato "${step.desc}" (seq=0x${seq.toString(16)})`);
      logEntry('tx', bytes);
    } catch (err) {
      logInfo(`Handshake: errore su "${step.desc}": ` + err.message);
    }
    await new Promise(r => setTimeout(r, 200)); // piccola pausa tra i messaggi
  }
  logInfo('Handshake completato. Prova ora "Invia parametro".');
}
